# libcamera support for the AR1335

libcamera will refuse a sensor it has no *CamHelper* for, so even a perfectly
working kernel driver produces `No cameras available!` until this is in place.
Two pieces are needed, and only one of them can be built without hardware.

## 1. `cam_helper_ar1335.cpp` — complete

Tells libcamera how to convert between the AGC algorithm's world (real gain,
exposure in time) and the sensor's (register codes, lines).

This is exact, not approximate. The AR1335's `GLOBAL_GAIN` register uses a
banded coarse/fine encoding that is **not monotonic** in the raw value, which
would break the AGC's search. The kernel driver therefore exposes
`V4L2_CID_ANALOGUE_GAIN` in linear 1/1024 units and does the banded conversion
itself, leaving this helper with a trivial, monotonic mapping:

```cpp
gainCode(g) = g * 1024        // 1024 == 1.0x
gain(code)  = code / 1024
```

`frameIntegrationDiff` is 1 line, matching the driver's exposure cap of
`FRAME_LENGTH_LINES - 1`. No embedded data is emitted by the vendor mode
sequences, so libcamera counts frames instead of parsing per-frame registers.

## 2. `ar1335.json` — a starting point, not a calibration

Generated by `tools/gen-tuning.py` from Raspberry Pi's IMX519 tuning, the
closest sensor they ship (same class of small-pixel, high-resolution Bayer
part).

Carried over as reasonable defaults: `agc`, `awb`, `contrast`, `denoise`,
`sharpen`, `noise`, `geq`, `dpc`, `lux`, `ccm`.

**Deliberately neutralised: `alsc` (lens shading).** Shading is a property of
the lens and module, not the sensor. Applying IMX519's tables to a different
optic would introduce colour and brightness errors across the frame, so the
tables are flattened to 1.0 — images start uncorrected rather than wrongly
corrected.

### Calibration status

| Item | State |
|---|---|
| `black_level` | ✅ **measured: 2688** (42 LSB at 10 bit) |
| `rpi.awb` `ct_curve` | ⚠️ **anchored** to the sensor's measured response at one point; CT labels still assumed |
| `rpi.alsc` (lens shading) | ❌ neutralised, needs a flat white field |
| `rpi.ccm` | ❌ still IMX519's, needs a colour chart |
| `rpi.lux` references | ❌ still IMX519's |
| `rpi.noise` | ✅ **measured** (photon transfer, see below) |

#### Black level — measured

Originally guessed at 4096 by copying the IMX519. Measured from raw AR1335
frames the pedestal is **2688** (42 LSB at 10 bits). 4096 is close to the
*median* of a normally exposed frame, so the ISP over-subtracted and crushed
the weakest channel: blue fell from 1846 to 374 and images had essentially no
blue (B/G = 0.10). Corrected → B/G = 1.10.

#### Noise — measured by photon transfer

`tools/measure-noise.py` captures two frames of a static scene and subtracts
them. The scene cancels exactly, leaving only noise, so no target is needed -
it works on whatever the camera happens to see.

| | reference_constant | reference_slope |
|---|---:|---:|
| inherited from IMX519 | 0 | 3.8 |
| **measured on this AR1335** | **15.4** | **1.769** |

The inherited pair claimed zero read noise and more than twice the shot-noise
slope, which would over-denoise highlights and under-denoise shadows.

Two measurement traps worth knowing, both found the hard way:

* **Mains flicker.** With shutter pinned at 20000 us the two frames differed by
  3-10% and the "noise" was really 120 Hz ripple. US mains flickers at 120 Hz
  (8333 us), and 20000 us is 2.4 cycles - a beat. At **25000 us (3 whole
  cycles)** frame-to-frame drift fell from 104 to 4. The tool now refuses a
  pair that drifts more than 2%, rather than reporting flicker as noise.
* **Quantisation.** Estimating sigma as a percentile of |difference| looks
  robust but picks an actual sample value, so with only a few LSB of noise it
  snapped to multiples of 1 LSB (45.25 in these units) and the fit followed the
  quantisation. A sigma-clipped standard deviation averages over the whole bin
  and is continuous; the residual improved from 15.3 to 5.4.

#### Chart calibration attempt — white balance stored, matrix not

Measured from the DKK chart via `tools/detect_chart.py`, which locates the 18
patches rather than assuming a rigid grid - necessary because the lens bows the
chart and a hand-held rig is never square. It fits a quadratic surface mapping
(column,row) to image position, so barrel distortion and rotation are absorbed
and undetected patches are interpolated.

**Stored on the camera EEPROM:** `r_over_g = 1.21808`, `b_over_g = 0.24073`.
The grey wedge validated - monotonically descending, and the four mid greys
agreed to within 3% in R/G.

**The colour matrix was computed and then discarded**, because it scored a mean
dE76 of 32 (good is under 3). Five patches - the cyan, blue and magenta ones -
read at the noise floor and could not be measured, and they are exactly the
patches that constrain a matrix. A matrix fitted without them is degenerate:
the one produced mapped blue output mostly from the green input. Storing it
would have been worse than storing nothing, so the tool now gates on quality
and keeps only the white balance.

Two things that capture needed and did not have:

* **Exposure for the blue channel.** This sensor's raw B/G is about 0.27, so
  blue-dominant patches sit near black. They need more exposure even at the
  cost of clipping the white patch, which can be dropped.
* **Less veiling glare.** The L*=0 patch read 22-30% of white. Subtracting the
  black patch recovered the grey wedge (total error against the expected
  reflectances fell 86%), but glare that large still buries the dark patches.
  Shade the lens and darken the surroundings.

#### The borrowed CCM is actively harmful here

Measured on the chart's grey patches:

| matrix | mean grey error | worst |
|---|---:|---:|
| IMX519's CCM | 15.9% | 21.7% |
| identity | **11.5%** | **14.5%** |

Its rows sum to 1, so it preserves a *perfect* neutral - but it amplifies any
residual white-balance error by about 40%. Until a real matrix is measured
there is a genuine choice: keep IMX519's for more saturated (if inaccurate)
colour, or use identity for a known, minimal transform and better neutrals.
For a science payload identity is arguably the better default, since ground
processing can apply a proper matrix later. Currently IMX519's is installed.

#### AWB — anchored, needs multi-illuminant refinement

The AR1335 is far more red-sensitive than the IMX519. Measured raw ratios are
**R/G = 1.16, B/G = 0.32**, while the borrowed `ct_curve` only spanned
R/G 0.39–0.73. The operating point was *outside* the curve, so AWB extrapolated
and went the wrong way: raw red was already dominant yet AWB applied a red gain
of 1.24, ending at R/G = 1.38 in the output.

`tools/fit-awb-curve.py --anchor` rescales the borrowed curve so it passes
through the measured point, keeping its shape (how ratios vary with CT, which
is driven by the illuminants and transfers between sensors) while moving it
onto this sensor's response. Result: AWB now picks gains [0.894, 2.796], reports
a plausible 3341 K, and the output sits at R/G = 1.02, B/G = 0.90 — against an
ideal of 0.97 / 0.99.

**What is still assumed:** the colour temperature *labels*. The anchor used an
assumed 3174 K for the room lighting, so AWB's reported CT is only as good as
that guess, and accuracy degrades away from this one illuminant.

**To finish it properly** — point the camera at a neutral grey or white card
filling the centre of the frame, under two or three different illuminants of
known colour temperature, and for each:

```bash
python3 tools/measure-awb.py --ct 2700     # e.g. warm indoor lamp
python3 tools/measure-awb.py --ct 4000     # e.g. cool white LED
python3 tools/measure-awb.py --ct 6500     # e.g. daylight through a window
```

Collect the `r_over_g` / `b_over_g` values into a JSON list and fit:

```bash
python3 tools/fit-awb-curve.py --points awb-points.json --install
```

That replaces the assumed shape with a measured one and makes the reported
colour temperatures real.

Raspberry Pi's `ctt` (camera tuning tool) automates most of this once frames
can be captured.

## Two traps when rebuilding

**`ninja install` overwrites the tuning file.** It installs
`src/ipa/rpi/pisp/data/ar1335.json` from the source tree, silently replacing a
tuned copy with whatever the tree happens to hold. That reverted a calibrated
black level and AWB curve once and showed up only as the colour going wrong
again (R/G 1.02 -> 1.69). Keep the two in step after any tuning change:

```bash
cp libcamera/ar1335.json libcamera-src/src/ipa/rpi/pisp/data/ar1335.json
sudo cp libcamera/ar1335.json /usr/local/share/libcamera/ipa/rpi/pisp/ar1335.json
```

**Do not `rmmod`/`modprobe` the sensor driver while rp1-cfe is bound to it.**
The front end re-runs its async-complete path and registers its video nodes a
second time, which oopses in `media_device_register_entity` and leaves
processes stuck in uninterruptible sleep. Reboot instead. `bind` on its own is
safe - that is what `tools/ar1335-autodetect.sh` uses, and its `unbind` was
removed for exactly this reason.

## Sensor properties in libcamera

`camera_sensor_properties.cpp` gained an `ar1335` entry: 1.1 um unit cell and
sensor delays. Without it libcamera warned *"No static properties available"*
and *"No sensor delays found ... Assuming unverified defaults"* - the delays
tell AGC how many frames pass before an exposure or gain write takes effect,
and wrong values make it over- or under-shoot.

The unit cell size is from the datasheet. **The delays are the SMIA-style
defaults (2/2/2/2) and have not been measured on this part** - verify by
stepping exposure and counting frames before relying on tight AE behaviour.

The driver now also exposes `V4L2_CID_CAMERA_ORIENTATION` and
`V4L2_CID_CAMERA_SENSOR_ROTATION` from the overlay's `orientation`/`rotation`
properties, via `v4l2_fwnode_device_parse()`. That silenced libcamera's
*"the sensor kernel driver needs to be fixed"* warning.

## Building and installing

```bash
git clone --depth 40 https://github.com/raspberrypi/libcamera.git libcamera-src
cp libcamera/cam_helper_ar1335.cpp libcamera-src/src/ipa/rpi/cam_helper/
cp libcamera/ar1335.json           libcamera-src/src/ipa/rpi/pisp/data/
# add both filenames to the meson.build in each of those directories

cd libcamera-src
meson setup build --prefix=/usr/local --buildtype=release \
    -Dpipelines=rpi/pisp -Dipas=rpi/pisp \
    -Dgstreamer=disabled -Dqcam=disabled -Ddocumentation=disabled \
    -Dcam=disabled -Dlc-compliance=disabled -Dtest=false -Dpycamera=disabled
ninja -C build
sudo ninja -C build install
sudo ldconfig
```

Installing to `/usr/local` shadows the Debian package rather than replacing it,
so `sudo rm -rf /usr/local/lib/aarch64-linux-gnu/libcamera*` plus `ldconfig`
reverts to the distro build if anything goes wrong. Both carry SONAME
`libcamera.so.0.7`, so `rpicam-apps` links against either.

## Verifying the helper is present

```bash
strings /usr/local/lib/aarch64-linux-gnu/libcamera/ipa_rpi_pisp.so | grep ar1335
ls /usr/local/share/libcamera/ipa/rpi/pisp/ar1335.json
```
